# Forge identity switch — act sheet

**Purpose:** move agent sessions from the owner's forge login (admin) to a dedicated push-only machine user, and prove that no owner credential is left within the agents' reach. Written with role names so an adopter on GitHub can use it as its own setup sheet; the rule and the reasoning are in [`separation-of-duties.md`](separation-of-duties.md) §Forge identity, and `docs/adoption/vc-hosts.md` says how another host maps it.

**Status in this repo: not yet switched on.** This sheet ships ahead of the switch. The kit's own repo runs it only after two follow-on changes have landed: the control-plane design GO must bind to the reviewing login's Approve (after the switch the design commit's committer is the machine user), and dev CI must publish the public mirror (so the machine user never needs a mirror credential). Step 0 is the exception and can be done any time. An adopter whose repo has neither dependency can run steps 0 to 8 at once.

**Solo project:** a one-account project runs the agent under its own login. `sparkwright doctor` reports that as INFO, not a warning (declaring a ratification seat in `.kit/ratification-seats.conf` turns the INFO into a counted warning). The switch becomes worth its cost once a separate identity reviews.

**Roles:** *the owner* holds the admin login and the reviewing login; *the machine user* is a separate forge account with two-factor on, added as a collaborator with **push only** (never admin or maintain), and nothing on the public mirror; *the agent* is any agent session.

**Each step names its actor and ends with a proof.** The owner does only the steps the guard refuses an agent (forge login changes, secret-store entries, the SSH key on the account, the MCP connector, token issue and revoke); the agent does the rest on the owner's word. Never paste a token into a session, a file or a commit.

| # | Actor | Act | Proof |
|---|---|---|---|
| 0 | the agent, on the owner's word (first; any time; need not wait for the switch) | Take the personal-access-token export (`GH_TOKEN`, `GITHUB_TOKEN` or `GITHUB_PERSONAL_ACCESS_TOKEN`) out of the shell profile. It is a credential in every shell's environment, so it is the widest path and the cheapest to close. Removing it changes nothing the loop uses, because `gh` resolves the owner's stored login without it. | A new session's `sparkwright doctor` prints no `forge credential:` line naming a token variable. Record the date with step 8's proofs. |
| 1 | the owner | Issue the machine user's **classic** token with exactly `repo` and `workflow` (not `gh auth login`'s defaults, which add `gist` and `read:org`), expiry one year. `workflow` is needed because a control-plane PR that edits `.github/workflows/*` is otherwise refused at push. Renew once per expiry. | On the token's settings page: scopes `repo` and `workflow` only, an expiry date set. |
| 2 | the owner, dated | Remove every remaining owner credential from what the agents' OS user can reach: log both owner logins out of `gh`; delete the owner's `github.com` entries from the keychain; take the SSH key off the admin account (`ssh -T git@github.com` names whose key it is); disconnect the GitHub MCP connector, or reconnect it as the machine user. | `gh auth status` lists no owner login; the keychain has no owner `github.com` entry; `ssh -T git@github.com` does not greet an owner login. |
| 3 | the owner | Log `gh` in as the machine user and store its token as the `github.com` git credential. | `gh auth status` names the machine user and no other account. |
| 4 | the agent, on the owner's word | Set the agent's git author (the machine user's name and its forge noreply email) with `includeIf "gitdir:<dev-clone-parent>/"` for the dev clones plus repo-local config in the main checkout; do **not** use `--global`, so the owner's own commits are untouched. | `git log -1 --format='%an <%ae>'` in a fresh commit names the machine user; a commit made outside those paths still names the owner. |
| 5 | the owner, once | Revoke the formerly exported personal access token on the forge (removing it from the profile does not invalidate copies in running shells or logs). Move the owner's forge browser sessions to a browser profile the browser-control extension is not connected to, or disconnect the extension from agent sessions; the connector change is account-wide, so choose knowingly. Run the owner's rare admin scripts (branch-protection apply and the live protection read) with `GH_TOKEN` from a credential the agents' user does not hold, or use the browser: they honour `GH_TOKEN` but unset `GH_CONFIG_DIR`, so a separate config directory does not carry the owner's login. | The old token's page shows it revoked; the agent's browser tools list no signed-in owner forge session. |
| 6 | each session | `sparkwright doctor --as agent`. | Exit 0, naming the machine user with `push` on the repository; the advisory lines list no stray token variable. Exit 1 means the session holds admin, maintain, no push, or an unreadable permission, or `gh` is unauthenticated or missing; exit 2 (UNVERIFIED) means the host has no forge adapter, origin's push URL names another repository, or the token is an App or CI token that cannot read its own identity (HTTP 403). The check reads the literal origin host, so an SSH host alias reports no adapter. |
| 7 | one session | Push a throwaway branch, read its actor from the repository activity API (read-only), then delete the branch. Confirm `ssh -T git@github.com` does not authenticate as an owner login, and that the MCP connector's `get_me` is not an owner login. | The activity record's actor is the machine user; the `ssh -T` and `get_me` answers name no owner login. |
| 8 | the owner | Record steps 0 to 7's proofs where the project keeps its decisions. Update the project's own runbook if the switch changed deploy-relevant configuration, and the ratification-seat descriptions that say the seat is "the same human as the author" (they stop being true of the author once it is the machine user): `MATURITY.md` (the separation-of-duties line), the project's threat model (its separation-of-duties row) and `docs/operations/separation-of-duties.md` (the paragraph on this repo's ratification seat). | The proofs are recorded; the residual (an admin login within the agents' reach) closes under the stated ceiling (one shared OS user is a strong seatbelt, not a boundary). |

## After the switch

The next slice should push, open a PR and run `land` under the machine user, with the reviewing login approving; `gh api repos/<owner>/<repo> --jq .permissions` run as the machine user shows no admin and no maintain.

## Rollback

Step 3 reversed: log `gh` in as the owner's login again. No kit change is needed. (Rolling back reopens every path in step 2; record why.)

## Honest ceiling

`sparkwright doctor` sees only the credential `gh` resolves. It cannot see the MCP connector, a token in another variable, the SSH key, or git's keychain entry, which is why steps 2, 5 and 7 are probes of their own. On one shared OS user the result is a strong seatbelt, not a boundary: anything the owner later stores on that user is reachable again. A separate OS user for agent sessions, holding only the machine user's credentials, is the real boundary and is a separate, heavier move.
